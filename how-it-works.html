How it works

One runtime.
Two ways in.

A port needs two things fn64 provides and your game does not: native code for the game’s functions, and a runtime for everything those functions call. Here is what each stage produces.

Choose your starting point ↓ Read the architecture ↗

From evidence
to execution.

Each stage has a concrete job and a visible output. That makes the pipeline easier to replace, test, and improve without hiding uncertainty in a monolithic tool.

  1. 01 / DISCOVER

    Recover the map

    Analyze a local ROM, retain proven facts, and keep a named blocker on every unresolved bank.

    OUT → content-free metadata
  2. 02 / RECOMPILE

    Translate the code

    Turn MIPS functions into typed Rust runners: one native function per MIPS function.

    OUT → host-native code
  3. 03 / EXECUTE

    Serve the ABI

    Link recompiled code to a clean-room Rust implementation of its expected runtime surface.

    OUT → running game logic
  4. 04 / PRESENT

    Render and play

    Connect graphics, audio, input, and platform integration through explicit backend seams.

    OUT → native application
  5. 05 / PROVE

    Keep the receipts

    Grade ABI shape, code generation, deterministic behavior, and release gates with executable checks.

    OUT → reviewable evidence

Pick a route

Meet your project
where it is.

ROUTE A / GENERATED CODE

You already use N64Recomp.

Keep its generated RecompiledFuncs/*.c. fn64’s build harness prepares and compiles those functions, registers their sections, and links their _recomp calls to the Rust ABI implementation.

  • The generated game code remains the N64Recomp C lane
  • A real C caller validates the external ABI
  • Your local ROM still supplies game data at runtime
ROUTE B / LOCAL ROM

You do not have a finished decomp.

fn64’s Rust lane recompiles the locally supplied ROM into typed runners. fn64-discover can recover supporting function and section metadata without treating incomplete evidence as certainty.

  • You can start before the decomp is finished, and see exactly what is still unproven
  • Unresolved sites remain visible as named blockers
  • Generated runners link directly to the Rust execution runtime
