Run it.#

The shell builds without any game content. It refuses to open an empty window and tells you what it needs instead.

No ROM, no game content

cargo run -p fn64-shell -- --demo

Drives the real window, framebuffer conversion, and overlay from a synthetic RDRAM field, so the UI stack stays verifiable in a checkout with nothing to boot.

With your own ROM and N64Recomp output

RECOMPILED_DIR=.../OOTU/RecompiledFuncs \
ROM=.../oot-ntsc-1.0.z64 \
cargo run -p fn64-shell

Same intake contract as examples/oot-boot. Your ROM and everything derived from it stays on your machine.

fn64-discover

Start with the ROM, not a finished decomp.#

fn64-discover reads a local ROM and recovers function and section metadata. You do not need a finished decomp to start, and what it cannot prove it refuses to claim. Today’s graded results still lean on donor ROMs and answer keys from existing decomp projects. Cold-start discovery on an unstudied ROM is the open frontier, and fn64’s own docs say so.

Boot-bank function recovery, graded against public decomp answer keys. As of August 2026.

Recall is what discovery found. Wrong is what it got wrong, and it is zero on every title. Missing a function costs you work; claiming a boundary that isn’t there costs you a debugging session chasing a ghost. Graded, not blind: each run uses a donor ROM and an answer key from an existing decomp project.

What’s in the box.#

One workspace, separate crates, each publishable on its own. If you only want the ABI surface, you only take fn64-abi.

fn64 crates and their roles
CrateRole
fn64-runtimeScheduler, OS message queues, timers, PI/SI/VI/AI plumbing, rdram model, overlays
fn64-abiThe extern "C" surface recompiled code links against
fn64-shellThe executable: window, input, audio out, ROM intake
fn64-discoverROM discovery: symbol and section metadata without a decomp
fn64-cpu-runtimeLinked typed execution runtime for generated VR4300 Rust runners
fn64-renderBackend-neutral render seam and ordered microcode admission
fn64-render-referenceDeterministic pure-Rust backend, software rasterizer, VI reference path
fn64-render-rt64FFI bridge to RT64. All C++ interop stays quarantined here
fn64-audioRSP audio ucode execution
fn64-diffThe first-divergence comparator. Pure, no I/O
fn64-certificationCross-backend and native RT64 behavioral evidence gates

Three more (fn64-boot-harness, fn64-cpu-runtime-codegen, fn64-recomp) handle boot wiring, build-side codegen, and the N64Recomp comparison lane. Full table with dependency rules ↗

How the work gets done.#

We use agents heavily, and a human still reviews and merges every change. Both work from the same notes: written from our own debugging, public documentation, and MIT source, never from GPL code. We write down why a thing is the way it is, so the next person can argue with the reasoning instead of guessing at it from the diff.
