What it is

The runtime recompiled code calls into.

The game's functions become native code compiled into your binary, translated once, ahead of time — no interpreter left in the loop. What that code still needs is everything the game used to call into on real hardware: the scheduler, message queues, timers, DMA, save, input and audio. That's fn64.

An emulator reads the game's MIPS instructions and interprets or JITs them every frame, for as long as it runs. fn64 doesn't do that — it doesn't read your ROM's instructions at runtime; it answers the calls the recompiled code makes.

You supply
A ROM you own + N64Recomp output, or nothing.
fn64 supplies
The runtime those functions call into, the render seam, and the checks that grade it.
Crates

One workspace, seventeen crates, one runtime underneath.

Take only what you need — every crate publishes on its own. Want just the ABI surface? Take fn64-abi and nothing else. Each stage below writes an artifact you can inspect on disk, so you can re-run any one alone and leave the rest untouched. Discovery

Graded, not blind.

fn64-discover reads a local ROM and recovers function and section metadata — no finished decompilation required. Here is the recall on six titles, graded against public answer keys:

Wrong is zero on every title. A missing function costs you some work. A boundary claimed where none exists costs you a debugging session chasing a ghost — so discovery only claims what it can prove, and the wrong column stays at 0.

Rigor

Rigorous by design.

Strong types, a behavioral test suite, a validation bar, named gates. Built from first-hand debugging, public docs and MIT source — never GPL code. Much of the volume is written by AI agents in orchestrated waves; humans direct the work and hold the gates, and humans and agents clear the same checks under the same contract (AGENTS.md).

Strong types TRAPS LOUDLY

Typed Rust runners. Unknown behavior traps loudly instead of returning a plausible zero — past the implemented edge, the runtime names itself rather than guessing.

Behavioral test suite ASSERTS BEHAVIOR

A byte-match against the original ROM only proves the build reproduced it. fn64 also carries a behavioral test suite that asserts the recompiled output behaves correctly: c_smoke links the ABI with a real C caller, and the recompiler has per-instruction oracle suites.

Validation bar ONE GATE, ONE CLAIM

A deterministic fix needs 1 fresh regression run plus the suite it sits in — repeating identical work is not more evidence. A concurrency or timing fix states its failure model and falls back to repeated runs, 20 by default, only when nothing stronger closes the interleaving.

deterministic: one run + the enclosing suite
concurrency: repeated runs, ×20 default, if nothing stronger closes it
