01 · What it is

Not an emulator

An emulator reads the game's MIPS instructions and interprets or JITs them every frame, for as long as it runs. Static recompilation does that translation once, ahead of time — so there is no interpreter left in the loop.

The game's functions become native code compiled into your binary, and there is no interpreter in the loop. What that code still needs is everything the game used to call into on real hardware.

That is fn64. It does not read your ROM's instructions at runtime; it answers the calls the recompiled code makes — the scheduler, message queues, timers, DMA, save, input and audio.

You supply
A ROM you own + N64Recomp output, or nothing.
fn64 supplies
The runtime those functions call into, the render seam, and the checks that grade it.

03 · Stages

Five stages. Each writes a file you can look at.

Discover, Recompile, Execute, Present, Prove. Every stage writes an artifact to disk, so you can read what one produced, re-run that stage alone, and leave the rest untouched. Hue encodes stage — the same colour follows it everywhere on this page.

Discover

Recover function and section boundaries from a local ROM.

Recompile

Turn MIPS functions into native code — no interpreter in the loop.

Execute

Run under the typed runtime; unknowns trap instead of guessing.

Present

Draw through the render seam to the reference backend or RT64.

Prove

Grade the result against named evidence gates.

06 · Rigor

Rigorous by design.

Strong types, a behavioral test suite, a determinism bar, named gates — every claim on this page is checkable. Designed with decades of engineering experience and built clean-room, from first-hand debugging, public docs and MIT source — never GPL code. Much of the volume is written by AI agents in orchestrated waves; a human directs the work and reviews every change, and humans and agents clear the same checks under the same contract (AGENTS.md).

Strong types TRAPS LOUDLY

Typed Rust runners. Unknown behavior traps loudly instead of returning a plausible zero — past the implemented edge, the runtime names itself rather than guessing.

Behavioral test suite ASSERTS BEHAVIOR

Where other N64 projects verify correctness mainly by byte-matching the original ROM at build time, fn64 also carries a behavioral test suite that asserts the recompiled output behaves correctly.

Determinism bar CONSECUTIVE CLEAN RUNS

A deterministic fix needs 10 consecutive clean runs before it counts. A concurrency fix needs 20+.
