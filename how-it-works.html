How it works — two ways in

Two ways in.

A native port needs two things your game does not ship with: native code for its functions, and a runtime for everything those functions call into. fn64 supplies both. Which route you take in depends on what you already have in hand.

Routes

Pick a route

Both routes read your locally supplied ROM and converge on the same Rust runtime underneath. The difference is where the game’s functions come from.

Route A C lane — N64Recomp

You already use N64Recomp

Keep its generated RecompiledFuncs/*.c. fn64’s build harness prepares and compiles those functions, registers their sections, and links their _recomp calls to the Rust ABI implementation.

Game code
Stays in the N64Recomp C lane.
Validation
A real C caller links the static library and exercises the external ABI.
Game data
Your local ROM still supplies it at runtime.
Route B Rust lane — fn64-discover

You do not have a finished decomp

fn64’s Rust lane recompiles the locally supplied ROM into typed runners. fn64-discover recovers supporting function and section metadata without treating incomplete evidence as certainty.

Starting point
You can start before the decomp is finished, and see exactly what is still unproven.
Unresolved sites
Stay visible as named blockers rather than guessed boundaries.
Linking
Generated runners link directly to the Rust execution runtime.
Stages

What each stage produces

Five stages, separate crates. Each writes something you can look at, so you can swap or re-run any one without rebuilding the others. Hue encodes stage — the same colour follows each stage everywhere on this page and the home page.

01 Discover

Analyze a local ROM, retain proven facts, name unresolved ownership. Out: content-free metadata.

02 Recompile

Turn MIPS functions into typed Rust runners, one per MIPS function. Out: native code.

03 Execute

Link recompiled code to fn64’s Rust implementation of the N64 platform runtime it expects. Out: a frame and audio census.

04 Present

Draw graphics and mix audio through explicit, swappable backend seams. Out: a rendered frame.

05 Prove

Grade ABI shape, code generation and deterministic behaviour against executable checks. Out: graded evidence.

Checks

What you can check yourself

Five things in the repo you can run or read if you want to disagree with us. A deterministic fix needs one fresh regression run plus the suite it sits in; a concurrency or timing fix falls back to repeated runs — twenty by default — only when nothing stronger closes the interleaving. A green run proves only the gate it exercised.

c_smoke
Link-tests the ABI with a real C caller against the static library.
Instruction oracles
Generated callable bodies diffed against N64Recomp output.
scripts/lane-parity.sh
Compares the C lane against the Rust lane, and currently refuses to treat the legacy C output as the arbiter of correctness, because it has not earned that mechanically.
docs/PARITY-METHOD.md
The blind spot in each of those checks, written down. A differential you cannot run is not evidence.
docs/ROADMAP.md
Every known gap, named. Unimplemented behavior traps instead of returning zero.
Rendering

Present is a swappable seam

Graphics go through a backend-neutral seam, so the thing that draws is swappable and the thing that decides what to draw is not.

fn64-render
The seam itself: ordered microcode admission and completion inspection, with no backend assumptions.
fn64-render-reference
A deterministic pure-Rust backend with a software rasteriser. Slow, but it needs no GPU and produces the same frame every time.
fn64-render-rt64
An FFI bridge to RT64 for the fast path. All C++ interop is quarantined in this one crate.

The reference backend exists so there is something to compare against. It needs no GPU, no driver and no C++ dependency, so cargo test stays GPU-free and every run produces the same frame. A cross-backend pixel differential exists and works, but it is narrow and runs by hand rather than in CI, because RT64 needs Vulkan, D3D12 or Metal and the test machines do not have one. Widening it is open work, not a finished gate.

Your content

Your content stays local

Both routes keep game content and title-specific work in your project. This repository holds tooling and runtime code: no game assets, no ROM bytes, no recompiled game output. You supply the ROM, it is read locally, and everything derived from it stays on your disk and out of git.

The discovery tool only emits metadata, never game assets, so its output is safe to paste into an issue or commit to a public repo.

Licence

Permissive, and enforced by the build

fn64’s own code is MIT OR Apache-2.0. Ship it, fork it, embed it in a commercial product, relicense your own work on top of it.

The dependency tree is permissive throughout, with no copyleft, but it is not MIT-only: winit and cpal are Apache-2.0, so a build that wants a window and audio takes Apache terms. The debug overlay also embeds egui’s default fonts, which carry OFL-1.1 and the Ubuntu Font Licence. Neither is onerous, and both want attribution in anything you distribute.

The runtime is written clean-room — meaning from our own debugging notes, public documentation and MIT source only. GPL implementation code is not read, not referenced, not laundered.

That is enforced by the build rather than promised. N64Recomp’s generated C emits #include "librecomp/sections.h" unconditionally, because it was written for a GPL-3.0 runtime. fn64 ships its own header at that path and puts its include directory first, so the compiler resolves to the clean-room version even if the original is installed. Your generated code links against the Rust runtime unchanged, and the GPL implementation is never compiled in.

RT64 is MIT and stays behind an FFI boundary in its own crate, so a port that does not want the C++ dependency can take the reference backend and never link it.
