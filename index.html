Run your recompiled ROM as a native app.

fn64 is a Rust runtime for Nintendo 64 static recompilation. Your recompiled ROM calls into it for the scheduler, message queues, timers, DMA and overlay lifecycle, save, input and audio.

  • Boots Ocarina of Time today
  • Pre-alpha
  • MIT OR Apache-2.0

Not an emulator

An emulator reads the game’s MIPS instructions and interprets or JITs them while it runs. Static recompilation does that work once, ahead of time: the game’s functions become native code compiled into your binary, and there is no interpreter in the loop.

What that code still needs is everything the game used to call into on real hardware. That is fn64. It does not read your ROM’s instructions at runtime; it answers the calls the recompiled code makes.

You supply
A ROM you own, and either N64Recomp output or nothing at all.
fn64 supplies
The runtime those functions call into, the render seam, and the checks that grade it.

Who this is for

People building a native N64 port, at one of two starting points.

Already on N64Recomp
Your generated C runs, but it links against a GPL-3.0 runtime (ultramodern/librecomp). fn64 is a drop-in Rust runtime for the same generated code, MIT OR Apache-2.0, so the licence on your own port is your call rather than the runtime's.
No decomp yet
You have a ROM and no finished decompilation to recompile. fn64-discover recovers function and section boundaries directly from the ROM, and names what it cannot prove instead of guessing, so you can see the actual gap before you start.
Auditing what you'd depend on
Every crate is MIT OR Apache-2.0, the RSP audio interpreter is clean-room, and the one filename forced by N64Recomp's generated code (librecomp/sections.h) is fn64's own header, not the GPL one. See the licence page for what that means for your build.

Where fn64 sits

One ROM, two lanes in, one runtime underneath. The lane you take decides how your code gets generated; it does not change what it links against.

Run it

The shell builds without any game content. It refuses to open an empty window and tells you what it needs instead.

Without a ROM

cargo run -p fn64-shell -- --demo

Drives the real window, framebuffer conversion and overlay from a synthetic RDRAM field, so the UI stack stays verifiable in a checkout with nothing to boot.

With your own ROM

RECOMPILED_DIR=.../OOTU/RecompiledFuncs \
ROM=.../oot-ntsc-1.0.z64 \
cargo run -p fn64-shell

Same intake contract as examples/oot-boot. This repository holds tooling and runtime code: no game assets, no ROM bytes, no recompiled game output. Everything derived from your ROM stays on your disk.

Wrong is zero on every title. Missing a function costs you work. Claiming a boundary that is not there costs you a debugging session. Graded, not blind: each run uses a donor ROM and an answer key from an existing decomp project, so cold-start discovery on an unstudied ROM is still the open frontier.

How the zero holds

Discovery only claims a boundary it can prove, and the passes are separable so you can see which one made a claim.

Delta-vote admission
Candidate tables are probed at a fixed stride. A table is admitted only when enough records agree on their field deltas, so a coincidental run of plausible values is rejected.
Prologue refinement
A prefix matcher flags likely function entries, then each boundary is pulled back to the preceding terminator. A candidate without one is not claimed.
Authority closure
Proof propagates only along call edges with incoming-edge evidence. Anything the closure cannot reach stays unresolved rather than being inferred.
Named blockers
Every unresolved bank keeps a blocker naming why it stopped, so a gap is a fact you can read rather than silence.

Stages

Each stage writes a file you can look at, so you can re-run one without rebuilding the others.

Discover
Analyze a local ROM, retain proven facts, keep a named blocker on every unresolved bank.
Recompile
Turn MIPS functions into typed Rust runners, one native function per MIPS function.
Execute
Link recompiled code to a clean-room Rust implementation of the runtime surface.
Present
Graphics, audio, input and platform integration through explicit backend seams.
Prove
Grade ABI shape, code generation and deterministic behavior with executable checks.

Crates

One workspace, separate crates, each publishable on its own. If you only want the ABI surface, you only take fn64-abi.

fn64-runtime
Scheduler, OS message queues, timers, PI/SI/VI/AI plumbing, rdram model, overlays.
fn64-abi
The extern "C" surface recompiled code links against.
fn64-shell
The executable: window, input, audio out, ROM intake.

Status

Ocarina of Time boots in a windowed app with the RT64 renderer and working input. Audio is still broken (R5) and the outdoor gameplay eye-gate is unmet (R3b). Both are tracked in the roadmap, which is the honest place to look before deciding whether fn64 is ready for what you want to do.

Pre-alpha means the runtime surface is implemented as far as shipping ports have needed, and no further. Anything past that edge traps and names itself rather than returning a plausible zero, so you find the gap instead of debugging a ghost.

How the work gets done

Most of the code is written by agents in orchestrated waves, and a human reviews and merges every change. Both work from the same AGENTS.md: written from our own debugging, public documentation and MIT source, never from GPL code. A deterministic fix needs 10 consecutive clean runs before it counts; a concurrency fix needs 20 or more.

If you want to check any of that rather than take it on faith, the checks are listed here.
