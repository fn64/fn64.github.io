Not-AI-generated: voice and shape

Two separate problems. Voice — the site borrowed the README's formal register and dropped its human one. Shape — nearly every section is an evenly-spaced card grid, which is the default silhouette of a generated landing page.

Two corrections to things I said earlier. (1) The four F-words are the project's own README table, not a site invention — but that doesn't make them good web copy. (2) I proposed “Rust is the mechanism, not the pitch” and “Discovery fails honestly” as the human voice to copy. Wrong. Those are not-X-but-Y and abstract-noun-plus-adverb — aphorisms that sound like insight while asserting instead of informing. The README has the same problem the site does. It is not a clean source of voice.

What's actually human in the README

Not the aphorisms. The unglamorous, specific, faintly embarrassing bits — the ones written to inform rather than to land.

Aphorisms — do not copy these

“Rust is the mechanism, not the pitch.”

“Discovery fails honestly.”

“Evidence over optimism.”

“A project people can join.”

Every one is a construction, not a statement. not-X-but-Y, noun+adverb, noun-over-noun. They read as written-to-be-quoted, which is the tell.
The real voice

“audio is still broken (R5) and the outdoor gameplay eye-gate is unmet (R3b)”

“boots OoT … in a windowed shell”

“a scheduler handoff that lets two ‘only’ threads run at once”

“a lost function that fell off the end of its own C body”

Specific, unglamorous, cites its own ticket numbers. Nobody writes “eye-gate is unmet (R3b)” to impress you — which is exactly why it convinces.

Shape: the card-grid problem

26 grid-template-columns declarations. Values 4-up, questions 3-up, stats 2-up, pipeline 5-up, plus two checklists. Alternating bands of evenly-spaced cards is what a generated page looks like — regardless of how good the words inside are.

Now — 3-up rhetorical questions
Built for N64 port builders

Already using N64Recomp?

Link your generated C against a typed Rust ABI…

Starting from a ROM?

Recover functions and section metadata…

Trying to trust the result?

Every claim has a test beside it…

Three parallel questions in a 3-up grid is a template slot, and “Every claim has a test beside it” is a slogan — it asserts rigor instead of showing any.
Instead — show the thing

Two ways in, depending on what you already have:

# you have N64Recomp output already
fn64 build --recomp-dir RecompiledFuncs/

# you have a ROM and no decomp
fn64-discover game.z64 --prove-owners
fn64 build --from-discovery

Either way the generated code links against the same fn64-abi crate. Your ROM never leaves your disk.

A developer learns more from two commands than from three cards asking them rhetorical questions. Shows the fork in the road literally.

Slogans vs. specifics

Now

“Every claim has a test beside it: a real C caller links the library, and generated code is diffed against N64Recomp instruction by instruction.”

“Unimplemented behavior does not silently return zero. It traps and names itself, so you find the gap instead of debugging a ghost.”

The first is a slogan with the evidence bolted on after a colon. The second is close — but “debugging a ghost” is a flourish.
Instead

When the runtime hits something it hasn't implemented, you get this:

thread 'guest' panicked at fn64-runtime/src/os/mq.rs:214
unimplemented: osSetEventMesg(OS_EVENT_PRENMI)
  called from 0x8003a1c0 <Main_ThreadEntry+0x4c>

Symbol and call context, not a silent zero. Every gap we know about is in docs/ROADMAP.md.

Show the panic. One real trace proves the claim the slogan was asserting, and it is the single most convincing thing you can put in front of a runtime developer.

What a developer-built page looks like structurally

Less uniform, denser, willing to be plain. Not every section needs to be a band of cards with a kicker above it.

Shape sketch

1. What it is — one paragraph, no kicker. What fn64 is and what it isn't (not an emulator).

2. Get started — the two commands, in a code block, immediately.

3. Status — plain prose about what boots and what's broken. Links to the roadmap.

4. Discovery — the table, then the animation showing how wrong == 0 is enforced.

5. The stack — the crate table straight from the README. Devs want to know what links against what.

6. Contributing — plain prose, licence, links.

Six sections, maybe two of them card-shaped. Kickers on none or one. The eye should land on a code block or a table within the first screen and a half.

The single biggest change: get a command or a real output on screen early. Right now you scroll through three prose sections before anything concrete appears.
